# 从一次 Codex 项目消失故障 提炼可复用的恢复流程

> 待审核稿，尚未发布到稀土掘金。案例来自 2026-10-21 的 Windows 排查。建议分类和标签：开发工具、Codex、工程实践；以发布时平台实际选项为准。

这次故障的表象很集中：重新打开 Codex，本地项目不见了，原项目聊天全部挤进“最近”。真正的排查重点，是分清界面组织记录和实际内容有没有同时丢失。

## 用证据缩小范围

分组设置已是按项目，切换显示方式解决不了问题。旧聊天仍能读取，抽查目录也存在，所以没有先重装或重建项目内容。

继续检查时发现，启动日志记录状态读取失败，JSON 中有无效空字符。项目缓存为空，但数据库保留了项目定义。这个组合支持重建组织记录的方向，却不能证明文件为何损坏。升级、强制退出或第三方工具都不能只凭时间先后被写成根因。

## 修复程序也需要独立的执行环境

首次程序的设计是“等待 Codex 退出后写入”。但它本身运行在 Codex 管理的执行会话中：宿主退出，修复进程也停止。用户重启后没有变化，因为程序并没有到达写入阶段。

后来改成从文件资源管理器独立启动，确认应用退出后再读取最新状态、备份和写回，才完成了配置恢复。这里有两个容易混淆的状态：预检通过不等于实际修改已提交，后台启动也不等于进程能在宿主退出后继续运行。

## 通用化需要保留停止条件

最终流程可以复用：

1. 分诊：账号、主机、分组、过滤、归档。
2. 取证：状态是否可解析，有没有项目定义及明确归属。
3. 备份：保存现场，区分故障快照和健康备份。
4. 生成本次清单：保留标识，不内置某次事故的固定数据。
5. 副本验证：检查结构、冲突、目录边界与无关设置。
6. 独立执行：应用关闭后写回，重新读取验证。
7. 应用验收：项目、抽查聊天和再次重启。
8. 失败回退：使用明确对应的一组备份。

当数据库版本不支持、归属冲突、文件本体丢失或权限检查失败时，应该停止自动写入。扩大权限、猜测字段或把所有 cwd 相同的会话塞进一个项目，都不能替代证据。

## 首版工具为什么默认只读

问题库提供 Python 标准库实现的诊断工具：

```sh
python tools/codex_doctor.py
python -m unittest discover -s tests -v
```

工具只输出计数、结构和错误类别，不读凭据或聊天正文、不联网、不改 Codex 状态。它能报告非法 JSON、缓存缺失的线索和多份数据库候选，但不会替使用者选择活动库或合并数据。

测试用合成记录覆盖损坏状态、旧表结构、多数据库、摘要脱敏和输入不变。真实案例仍需单独验收：本例恢复了 9 个项目记录和 24 条归属配置，应用接口能够读取；数据库同步与完整二次重启没有被当作已完成验证。
