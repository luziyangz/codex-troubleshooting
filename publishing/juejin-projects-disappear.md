# Codex 项目消失、聊天都在最近：一次状态恢复实录

一次重新打开 Codex 后，项目列表不见了，过去的项目聊天全部集中到“最近”。重启应用没有恢复。最后定位到启动时全局状态 JSON 解析失败，并从仍有效的记录中恢复了项目和聊天归属配置。

这篇文章按问题、原因和解决步骤记录过程。

## 问题：侧栏消失，不一定是数据删除

环境是 Windows。本次侧栏原本就按项目分组，抽查的原项目目录存在，旧聊天也能读取。需要分别确认四层状态：

| 层次 | 检查什么 | 本次观察 |
| --- | --- | --- |
| 视图 | 账号、主机、分组、过滤、归档 | 仅改分组不能解决 |
| 文件 | 原项目目录与文件 | 抽查仍存在 |
| 聊天 | 旧聊天能否打开 | 抽查可以读取 |
| 组织关系 | 项目定义和聊天归属 | 没有正常加载 |

如果只是入口被移除，先通过“添加项目”选择原目录。这也是 [OpenAI 故障排查文档](https://learn.chatgpt.com/docs/reference/troubleshooting)给出的处理方式之一。确认不是视图或入口问题后，再进一步检查状态文件。

## 原因：从启动日志定位

故障当天的启动日志包含这段信息，省略了完整堆栈：

```text
2026-10-21T05:53:50.665Z warning [global-state] Failed to load global state
errorName=SyntaxError
errorMessage="Unexpected token '\u0000', ... is not valid JSON"
```

UTC 时间对应北京时间 13:53:50。`\u0000` 是空字符，状态内容没有通过 JSON 解析。后续读取到的项目缓存缺失，但数据库仍保留项目定义和根目录。

因此，这次能确认的直接原因是全局状态读取失败。**空字符为什么出现仍然未知**，没有证据将它归因于升级、强退或第三方工具。

容易误判的一点：应用后来可能写出合法的新 JSON。当前文件能解析，不代表故障发生时也正常，更不代表项目记录已经完整。

## 从哪些文件开始查？

本次实际状态目录为 `E:\Codex\home\.codex`，关注这些相对路径：

```text
.codex-global-state.json
.codex-global-state.json.bak
state_5.sqlite
sqlite\codex-dev.db
```

这是现场观察到的内部结构，不是稳定的公开 API。先核对 `CODEX_HOME`；未设置时再检查用户目录下的 `.codex`。不同版本的名称和结构可能不同。本次还存在根目录和 `sqlite` 子目录中的两个状态数据库，不能仅凭修改时间挑一个写入。

本次 Windows 安装的日志位于：

```text
%LOCALAPPDATA%\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\Local\Codex\Logs\2026\10\21\
```

可以在 PowerShell 做只读检查，先替换为自己的实际状态目录：

```powershell
$codexDir = 'E:\Codex\home\.codex' # 示例，替换为实际路径
$statePath = Join-Path $codexDir '.codex-global-state.json'
try {
    $null = Get-Content -LiteralPath $statePath -Raw -Encoding UTF8 |
        ConvertFrom-Json -ErrorAction Stop
    '当前 JSON 可以解析，仍需核对项目记录和启动日志'
} catch {
    '状态读取或解析失败：' + $_.Exception.Message
}
```

在实际日志文件中搜索 `Failed to load global state` 和 `Unexpected token`，保留相关片段即可。

## 解决：分阶段恢复

### 1. 保存现场

备份状态 JSON、其备份文件、相关数据库和日志。运行中的 SQLite 使用备份接口创建一致快照，避免只复制主文件遗漏 WAL。给快照标注时间，区分故障现场与故障前的健康备份。

### 2. 优先使用应用支持的方式

少量项目可以重新添加原目录，再核对旧聊天归属。若有健康状态备份，先比较时间、版本和后续配置变化，在应用关闭后恢复匹配的文件。

### 3. 没有健康备份时，核对有效记录

本次从仍存在的 `projects`、`project_roots` 记录核对项目，保留原项目标识，在副本里重建相关配置。

配置层涉及 `local-projects` 和 `thread-project-assignments` 等字段，但不能把它们当成跨版本修复协议。合并时保留未知字段和正确设置；多根目录、worktree、迁移目录和明确无项目的聊天要单独处理。

副本至少检查 JSON 合法性、项目标识、根目录、归属冲突和前后差异。只有记录足够、结构匹配时才写回；否则停止修改并保留现场。

### 4. 执行器独立于被修复的应用

第一次恢复脚本在 Codex 执行会话里等待应用退出。应用关闭后，脚本也结束了，结果停在 `waiting_for_exit`，实际上没有写入。

后来的做法是从资源管理器启动独立程序：等待 Codex 进程退出，重新读取并备份最新状态，检查输入是否变化，按本次清单合并，通过临时文件刷新落盘后替换目标，再解析验证并重新打开应用。

```text
副本预检 → 应用外启动 → 关闭目标应用 → 备份最新状态
       → 检查现场变化 → 合并与替换 → 重新解析 → 应用验收
```

“进程启动”“等待退出”“配置写入”“应用读取成功”是不同状态。修复记录必须能区分它们，不能只给一个笼统的成功提示。

## 结果与验收边界

本次在 2026 年 10 月 21 日 14:33 恢复了 9 个项目记录、24 条聊天归属配置。应用接口重新列出项目，抽查旧聊天返回对应项目标识。

当时 SQLite 的 `threads.project_id` 仍为空，不能声称数据库字段已同步。也没有逐条人工打开全部聊天或完成第二次完整重启验收。

后续应检查侧栏、原目录、多个项目的旧聊天、无项目聊天是否被误分配，以及正常重启后结果是否保留。失败时先保存当前状态，再在应用关闭时回退到明确对应的修复前快照。

可复用的流程是：**先分诊，再取证；先备份，再预检；独立执行，分层验收。** 它适用于项目组织关系异常，不代表能找回已经删除的文件或聊天。
