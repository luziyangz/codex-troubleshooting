# Codex 项目消失 聊天都在最近 排查与恢复步骤

> 待审核稿。依据 2026-10-21 的 Windows 实测案例与公开文档整理，尚未发布到 CSDN。建议标签：Codex、故障排查、Windows、数据恢复。标签仅为编辑建议。

打开 Codex 后，原来的本地项目突然不见了，旧聊天却都出现在“最近”。遇到这种情况，先确认数据在哪里，再决定恢复方式。

项目文件夹、聊天记录、项目入口和聊天归属不一定存放在同一份记录里。入口没加载出来，并不能直接证明文件或聊天已经被删除。

## 先区分四种情况

| 现象 | 优先检查 |
| --- | --- |
| 项目还在，聊天只是平铺 | 侧栏分组设置 |
| 仅部分聊天不见 | 过滤和归档 |
| 大量本地项目不见，聊天仍能打开 | 本地状态、项目定义和启动错误 |
| 原文件夹或聊天本体也找不到 | 单独的数据恢复调查 |

如果只是不见了少数项目入口，官方说明给出的办法是重新添加原目录。不要为了恢复入口又创建一套新的项目文件。[官方故障排查](https://learn.chatgpt.com/docs/reference/troubleshooting)

## 这次案例为什么会出现

本例中，分组设置已经是按项目组织，旧聊天和抽查的项目目录都还在。启动日志出现 `Failed to load global state`，并报告无效空字符 `\u0000`。随后看到的本地项目缓存为空，但数据库仍有项目定义及根目录。

因此能确认的直接问题是状态解析失败，导致项目列表与聊天归属没有正常加载。文件为什么损坏仍然未知；不能直接归因于升级、强退或更换模型服务商。

## 恢复流程

第一步，核对账号、主机、实际状态目录、分组、过滤和归档。可以使用仓库内的只读工具辅助检查：

```sh
python tools/codex_doctor.py --codex-home /path/to/.codex
```

工具默认也会参考 `CODEX_HOME`。它输出结构与计数，不读聊天正文，不修改配置；“未发现结构异常”不表示所有项目已经恢复。

第二步，保存带时间戳的状态快照。运行中的 SQLite 数据库要用一致性备份方式处理，不能忽略 WAL。应用生成的 `.bak` 也可能已被故障状态覆盖，所以要有单独的历史备份。

第三步，从当前有效记录生成本次恢复清单，在副本中合并并检查。保留项目标识和已有正确关联，不用旧配置覆盖全部偏好。工作目录能提供线索，但不能作为把所有聊天自动归组的唯一依据。

第四步，从应用外独立启动恢复程序，再正常退出 Codex。退出后重新读取最新状态，备份、写入、读回验证，再启动应用。不同版本结构不一致时应停止写回，优先采用应用支持的恢复方式。

第五步，检查项目和抽查聊天，再正常重启一次验证是否保留。配置写入、应用读取和数据库字段同步是不同层面，验收记录不能混写。

## 为什么第一次重启没有效果

首次等待恢复的程序运行在 Codex 管理的执行会话中。退出应用时，它也一起被停止，结果一直停在 `waiting_for_exit`，没有真正写入。后来从文件资源管理器独立启动恢复器才完成写回。

这次配置恢复了 9 个项目记录与 24 条聊天归属，应用接口也读到了项目和抽查聊天的关联。SQLite 对应字段当时仍为空，因此没有把它写成数据库同步完成；也没有逐条人工打开全部聊天或完成第二次重启验收。

## 如何把经验复用给其他人

可复用的是“分诊、取证、备份、清单、验证、独立执行、验收、回退”的流程。某台电脑的绝对路径和固定项目列表不能变成通用补丁。

公开问题库：[codex-troubleshooting](https://github.com/luziyangz/codex-troubleshooting)。其中提供完整 SOP、只读工具、问题模板及适用范围；首版没有未经版本核对就自动改写配置的功能。
