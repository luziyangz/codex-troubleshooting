# Codex 项目突然消失、聊天全到最近：日志定位与恢复步骤

重新打开 Codex，侧栏里的项目不见了，以前按项目整理的聊天全部出现在“最近”。退出后重新打开，还是一样。

这是一次发生在 Windows 上的实际故障。排查后确认：抽查的项目目录和聊天内容仍在，启动时本地全局状态读取失败，项目列表和聊天归属没有正常加载。本文记录问题、证据和处理步骤。

## 一、先判断：入口消失，还是数据丢了？

先做四项检查：

1. 核对登录账号、工作区，以及本地或远程主机是否与之前一致。
2. 检查侧栏是否按项目分组，是否开启了搜索、过滤或归档视图。
3. 在资源管理器中打开原项目目录，确认文件存在。
4. 从“最近”打开两条旧聊天，确认内容仍可读取。

如果只是少数项目入口被移除，可以先使用“添加项目”，选择原来的目录。OpenAI 的[故障排查文档](https://learn.chatgpt.com/docs/reference/troubleshooting)也给出了重新添加原目录的方式；归档聊天则需要检查归档入口。

本次侧栏本来就是按项目分组，抽查的旧聊天和原目录也在，因此继续检查本地状态。

## 二、真正定位问题的日志

2026 年 10 月 21 日的启动日志中出现以下错误。摘录保留时间和错误信息，省略完整堆栈：

```text
2026-10-21T05:53:50.665Z warning [global-state] Failed to load global state
errorName=SyntaxError
errorMessage="Unexpected token '\u0000', ... is not valid JSON"
```

日志时间是 UTC，对应北京时间 13:53:50。`\u0000` 表示空字符，不能在这里构成合法的 JSON 内容。结合后续检查，项目缓存和原有聊天归属没有正常加载，但数据库里仍保留着项目定义和根目录。

**已确认的直接原因是全局状态解析失败；是什么造成空字符写入，目前没有证据确定。** 不能仅凭这个错误就认定是升级、强制退出、磁盘故障或某个第三方工具造成的。

### 状态文件在哪里？

本次机器实际使用的状态目录是：

```text
E:\Codex\home\.codex
```

排查时关注的相对路径如下。它们是本案例观察到的内部文件，不保证每个版本都有相同名称或结构。

```text
.codex-global-state.json
.codex-global-state.json.bak
state_5.sqlite
sqlite\codex-dev.db
```

第一项的实际完整路径是 `E:\Codex\home\.codex\.codex-global-state.json`。如果配置过 `CODEX_HOME`，先核对它；没有设置时，再检查当前用户目录下的 `.codex`。不要照抄本文的 E 盘路径。

本次 Windows 安装的桌面日志目录为：

```text
%LOCALAPPDATA%\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\Local\Codex\Logs\2026\10\21\
```

这个路径来自本次安装方式。其他安装方式、系统或版本可能不同，可先从应用提供的日志入口查找。

### 两个只读检查命令

在 PowerShell 中检查状态 JSON。这里会读取文件，不会修改配置：

```powershell
$codexDir = if ($env:CODEX_HOME) {
    $env:CODEX_HOME
} else {
    Join-Path $env:USERPROFILE '.codex'
}
$statePath = Join-Path $codexDir '.codex-global-state.json'
try {
    $null = Get-Content -LiteralPath $statePath -Raw -Encoding UTF8 |
        ConvertFrom-Json -ErrorAction Stop
    '当前状态 JSON 可以解析'
} catch {
    '状态读取或解析失败：' + $_.Exception.Message
}
```

查日志时，用实际找到的日志文件替换占位路径：

```powershell
Select-String -LiteralPath 'C:\实际路径\codex-desktop-xxx.log' `
    -SimpleMatch 'Failed to load global state' |
    Select-Object -First 3
```

**当前 JSON 可以解析，也不能排除之前出过问题。** 应用可能已经生成一份合法但缺少原项目缓存的新状态，仍需结合故障时的启动日志判断。

## 三、解决方案：按证据恢复项目和归属

### 1. 先备份，再修改

保存状态 JSON、`.bak`、相关数据库和故障日志，放入带时间戳的独立目录。运行中的 SQLite 要通过备份接口生成一致快照，不能只复制主文件而忽略 WAL。

区分“故障现场备份”和“故障前的健康备份”：现场备份用于撤销本次操作，本身可能已经处于项目消失的状态。

### 2. 优先评估应用支持的方式和健康备份

少量项目可以先重新添加原目录，再核对旧聊天归属。若有健康状态备份，确认时间、账号、主机和版本匹配，并检查是否会覆盖之后新增的设置。关闭应用后再恢复匹配的文件，避免直接用不明来源的旧文件覆盖当前目录。

### 3. 大量项目一起消失时，从有效记录建立清单

本次没有清空状态目录，而是从仍有效的项目定义中核对项目标识、名称、根目录和顺序，再检查聊天归属。

本案例的数据库有 `projects`、`project_roots` 表，配置中有 `local-projects`、`thread-project-assignments` 等字段。它们是这次排查的线索，不是跨版本修复协议。确认结构匹配后，先在副本里重建清单和配置。

不能只根据聊天工作目录自动分配全部聊天。项目可能有多个根目录，也可能存在 worktree、目录迁移、子代理，以及用户明确设为无项目的聊天。原有正确归属应保留，冲突项应单独判断。

本次只合并有证据的项目和归属，保留其他设置。副本需要检查 JSON、项目标识、目录、归属冲突和修改差异，再进入写回阶段。

### 4. 从应用外运行修复程序

第一次尝试让 Codex 执行会话里的脚本等待应用退出。结果 Codex 关闭后，等待进程也结束了；状态停在 `waiting_for_exit`，没有执行写回。

后来改为从资源管理器启动独立修复程序，流程如下：

```text
应用外启动修复程序
    ↓
正常退出 Codex，确认目标进程已停止
    ↓
重新读取并备份最新状态，检查是否发生变化
    ↓
按本次清单合并，在临时文件中写入并刷新落盘
    ↓
替换目标状态文件，再次解析验证
    ↓
重新打开 Codex，检查项目与旧聊天
```

关键是确认执行器确实能在应用关闭后继续工作。不能把“脚本已启动”当成“修复已完成”，也不能在应用运行时随意覆盖缓存文件。记录不足或结构不匹配时，应停止写回，保留现场。

## 四、这次恢复到了哪一步？

2026 年 10 月 21 日 14:33 的独立修复结果是：

- 恢复了 9 个本地项目记录和 24 条聊天归属配置。
- 应用接口重新列出了项目，抽查旧聊天返回对应项目标识。
- 当时 SQLite 的 `threads.project_id` 仍为空，不能声称数据库字段已经同步。
- 没有逐条人工打开全部 24 条聊天，也尚未完成第二次完整重启的持久性验收。

这些数量是本次结果，不是其他电脑应该恢复出的固定数量。

完整验收还包括：侧栏项目可见、根目录正确、抽查多个项目的聊天、原本无项目的聊天没有被误分配，以及再正常重启一次后仍保留结果。若写回后异常，在应用关闭时恢复明确对应的修复前快照，再检查日志。

## 五、遇到同类问题的处理顺序

**核对账号和视图 → 确认目录与聊天仍在 → 查启动日志 → 备份现场 → 优先使用应用支持的方式 → 必要时按当前版本重建配置 → 应用外执行 → 验收与重启复查。**
