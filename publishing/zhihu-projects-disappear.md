# Codex 项目突然没了，旧聊天全在“最近”，怎么恢复？

如果重新打开 Codex 后，项目列表消失了，过去按项目整理的聊天都跑到了“最近”，先确认原项目文件和旧聊天是否还在。这一步决定接下来应该检查显示与归属，还是进入数据恢复。

我这次在 Windows 上遇到的情况是：抽查的项目目录还在，旧聊天也能打开；退出再打开，项目仍没有出现。最后从启动日志定位到本地状态读取失败，恢复了项目列表和聊天归属配置。

## 问题可能出在哪一层？

先依次核对：

1. 是否登录相同账号、工作区和主机。
2. 侧栏是否改了分组，是否启用了过滤、搜索或归档视图。
3. 在资源管理器中能否打开原项目目录。
4. 从“最近”打开两条旧聊天，内容是否仍可读取。

如果只是项目入口被移除，可以通过“添加项目”重新选择原来的目录。这个方法也见于 [OpenAI 的故障排查说明](https://learn.chatgpt.com/docs/reference/troubleshooting)。聊天被归档时，则先检查归档入口。

本次并不是简单的分组变化：侧栏已经按项目分组，项目和聊天之间的组织关系没有正常加载。

## 原因是怎么确认的？

启动日志里有下面的错误。这里省略完整堆栈，保留关键证据：

```text
2026-10-21T05:53:50.665Z warning [global-state] Failed to load global state
errorName=SyntaxError
errorMessage="Unexpected token '\u0000', ... is not valid JSON"
```

时间是 UTC，对应北京时间 13:53:50。日志说明全局状态未能通过 JSON 解析，其中出现了空字符 `\u0000`。

进一步检查时，项目缓存缺失，但数据库仍保留项目定义和根目录。这些证据支持“状态读取失败，导致项目和归属没有正常加载”的判断。

**空字符为什么出现，目前仍没有证据确定。** 不能直接说是升级、强制退出、磁盘故障或第三方工具造成的。重启只能再次读取当前状态，不能保证补齐缺失的项目组织信息。

## 日志和状态文件在哪里找？

本次电脑使用的状态目录是：

```text
E:\Codex\home\.codex
```

里面关注的相对路径有：

```text
.codex-global-state.json
.codex-global-state.json.bak
state_5.sqlite
sqlite\codex-dev.db
```

如果设置了 `CODEX_HOME`，先检查对应目录；没有设置时，再检查当前用户目录下的 `.codex`。上面的 E 盘位置是本次环境，不是所有电脑的默认路径。文件名和结构也可能随版本变化。

本次 Windows 安装的日志目录为：

```text
%LOCALAPPDATA%\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\Local\Codex\Logs\2026\10\21\
```

在日志中搜索 `Failed to load global state`，可以找到相关错误。其他系统或安装方式可先使用应用提供的日志入口。

熟悉 PowerShell 的读者可以只读检查 JSON，替换示例路径后执行：

```powershell
$statePath = 'E:\Codex\home\.codex\.codex-global-state.json'
try {
    $null = Get-Content -LiteralPath $statePath -Raw -Encoding UTF8 |
        ConvertFrom-Json -ErrorAction Stop
    '当前 JSON 可以解析'
} catch {
    '读取或解析失败：' + $_.Exception.Message
}
```

当前 JSON 合法不代表故障时也合法。应用可能已经生成一份新的空状态，所以要结合故障时日志和项目记录一起判断。

## 实际应该怎么恢复？

**第一步，备份现场。** 保存状态文件、其备份和相关日志。运行中的 SQLite 数据库使用备份接口生成一致快照，不能只复制主文件。备份按时间分目录，标明是健康备份还是故障现场。

**第二步，优先尝试应用提供的方式。** 少量项目可以重新添加原目录；有健康状态备份时，核对时间、版本和后续设置变化，关闭应用后再恢复匹配的文件。

**第三步，没有健康备份时，从有效记录核对归属。** 本次从数据库保留的项目定义建立恢复清单，核对项目标识、名称、根目录和聊天归属。在副本验证后，再合并到最新状态中。

这一步不能直接复制别人的配置，也不能只看聊天工作目录就把所有聊天强行分组。多根目录、worktree、目录迁移，以及明确无项目的聊天，都可能让这种推断出错。结构不匹配或记录不足时，先停止修改。

**第四步，在应用关闭后写回，执行器要独立于 Codex。** 我第一次把等待退出的脚本留在 Codex 会话里；退出应用时，脚本也结束了，没有执行修复。

后来从资源管理器启动独立程序：确认应用已退出，重新读取并备份最新状态，检查输入是否变化，再通过临时文件写入和替换目标，重新解析后启动 Codex。

## 这次恢复结果，以及如何判断成功

本次在 2026 年 10 月 21 日 14:33 恢复了 9 个项目记录、24 条聊天归属配置。应用接口重新列出项目，抽查旧聊天返回对应项目标识。

这里也有明确的验证边界：当时数据库的 `threads.project_id` 仍为空；没有逐条人工打开全部聊天，也尚未完成第二次完整重启验收。因此，准确说法是配置已恢复，并完成了应用接口和抽样核对。

恢复后还应检查：项目是否显示、目录是否正确、多个项目的旧聊天能否打开、原本无项目的聊天是否被误分配，以及再正常重启后是否仍保留结果。失败时，在应用关闭后回退到明确对应的修复前快照。

遇到相似问题，可以按“确认数据仍在—排除视图问题—查日志—备份—恢复—重启验收”的顺序处理。详细步骤和只读工具放在 [codex-troubleshooting 问题集合](https://github.com/luziyangz/codex-troubleshooting)，作为补充资料。
