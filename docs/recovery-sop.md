# 项目列表与聊天归属的通用恢复 SOP

适用条件：项目入口或聊天分组异常，但原项目目录和聊天记录仍存在。下面的文件名来自已观察到的版本，不是稳定的官方数据接口；其他版本先核对结构。

## 1 确认问题范围

检查账号、工作区或主机、侧栏分组、过滤和归档；抽查项目目录及旧聊天。若文件或聊天本身丢失，先转入数据恢复。仅项目入口被移除时，可按 [官方说明](https://learn.chatgpt.com/docs/reference/troubleshooting#remove-a-project-from-the-sidebar) 重新添加原目录。

## 2 保存现场

确认实际状态目录，通常优先考虑 `CODEX_HOME`；未设置时再检查当前用户下的 `.codex`。保存状态文件、其备份、项目定义与脱敏日志线索，使用单独的时间戳目录。

观察到的文件包括 `.codex-global-state.json`、其 `.bak` 及 `state_*.sqlite`。运行中的 SQLite 数据库用备份接口创建一致快照，不只复制主文件而忽略 WAL。现场副本可能仍是损坏状态，必须与已验证的健康备份分开标记。

## 3 识别可恢复信息

检查 JSON 能否解析、项目定义及根目录是否仍存在、是否留有明确的聊天归属。状态已被重新生成为合法空对象时，当前 JSON 能解析也不能排除此前的读取失败，应结合启动日志判断。

保留项目原有标识；按当前记录制定本次清单。不能把某次案例的固定数量当作目标，不能仅凭聊天工作目录就把全部聊天自动分组。多根目录、目录迁移、worktree、子代理及明确无项目的聊天都需要单独判断。

## 4 在副本上验证

核对版本与字段结构；保留未知字段、已有正确归属及无关设置。只合并有证据的项目、排序、标识映射和归属字段。涉及迁移标记时，应先理解当前版本的行为。

验证 JSON、项目标识、目录边界、归属冲突及前后差异。副本验证通过表示方案可以进入执行阶段，不等于线上状态已经修复。

## 5 独立执行写回

从应用外启动恢复程序，再正常退出 Codex。恢复程序应确认目标应用已停止，避免缓存写回覆盖修复结果；它也不能依赖会随应用一起关闭的执行会话。

写入前再次备份并读取最新状态，检查输入是否在预检后发生变化。采用临时文件、刷新落盘和替换目标文件的方式写入，重新解析并核对目标文件，再启动 Codex。无法完成权限或进程检查时停止写入。

首版仓库只提供只读诊断工具，实际写回应由理解本次数据结构的人执行。没有与版本匹配的清单时，优先使用应用支持的恢复方式。

## 6 验收

- [ ] 项目重新显示，原根目录和文件正确。
- [ ] 抽查两个以上项目的旧聊天，内容与归属正确。
- [ ] 原本无项目的聊天没有被强行归组。
- [ ] 其他设置没有被旧配置覆盖。
- [ ] 再正常重启一次，组织结构仍然保留。
- [ ] 保存范围、时间、备份位置和未解决项。

配置文件写入、应用接口读取、侧栏显示、底层数据库字段同步是不同的验证层。验证了哪一层就记录哪一层，不能互相代替。

## 7 失败与回退

区分程序未启动、等待退出、权限失败、写入失败、被覆盖和载入失败。保留当前快照后，在应用关闭时恢复一组明确对应的修复前文件；不要拼接不同时点的配置与数据库。

回退到故障前的健康备份与撤销本次修改不是同一件事。修复前备份可能本来就是空项目状态，应标明它的作用。

## 8 后续维护

项目增删或目录变化后更新清单，更新应用前保留健康状态快照。`.bak` 会被后续写入替换，不能代替带时间戳的历史备份。不要为了取证公开整个状态目录。
